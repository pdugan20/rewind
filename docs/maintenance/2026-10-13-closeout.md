## Deployment safeguard

The prepared change gives the API and artwork Workers separate impact decisions in the trusted Deploy workflow. API-only source edits do not deploy artwork. Artwork source, assets, processor scripts, and configuration deploy artwork; shared authentication, storage, image helpers, TypeScript configuration, and root runtime dependencies conservatively affect both Workers. An import-closure test rejects artwork dependencies outside that boundary.

D1 remains a single migration-ledger action. When both Workers change, artwork still deploys before the API that consumes its RPC service. An explicit no-op or successful deployment is required for each Worker before the cumulative checkpoint advances. The existing CI trigger verification and exact source checkout remain required.

`npm run deploy:worker` and `npm run deploy:artwork` use the guarded deployment script. It requires clean, committed source reachable from `origin/main`, checks the active production version's Git provenance, refuses unknown or split/ambiguous production versions, and tags new uploads with the full source commit. A deployed source newer than the intended checkout also blocks replacement. The artwork processor identity is regenerated and checked before upload. The root `npm run deploy` checks provenance before its migrations, and CI performs the same check before remote migrations.

The source check recognizes only two audited legacy untagged versions: the API and artwork versions deployed from PR #320. Their exact IDs and source commit are in `scripts/deployment-baseline.json`. This is a bounded bootstrap, not permission to trust any untagged version. Do not update that file merely to clear a failed deployment. First reconcile the live code with Git and review the evidence.

`npm run deployment:check` is read-only. It reports the active version, recorded source commit, and intended commit for each Worker. These markers establish source lineage, not cryptographic verification of uploaded bytes. Direct dashboard uploads or bare Wrangler commands can bypass the wrapper; an unknown untagged version then blocks the next guarded release. Rollbacks and migrations still require their existing production approval.

The owner approved publishing this safeguard through a protected PR and merge. Release evidence belongs in that PR; the actual post-merge checkpoint must be verified before closing the batch.
